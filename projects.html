PortfoliU, Optimal Portfolio Construction via Convex Optimization

A full stack platform that turns Markowitz mean variance theory into a solver, a backtester, and a product.

View Live Platform Source Code

Overview

PortfoliU began as a question that most retail investing tools quietly avoid. Given a universe of assets, what weights should an investor actually hold, and can that answer be defended mathematically rather than asserted? Modern portfolio theory answers this with convex optimization, so I built the platform around a real solver instead of a heuristic. A user selects a set of tickers, chooses an objective and a set of constraints, and the backend returns the optimal weight vector along with the efficient frontier that surrounds it.

What began as a coursework project inside the SEO Tech Developer Program grew into the piece of engineering I have spent the most time on. I led the backend, which meant owning the optimization engine, the risk models, the market data layer, the backtesting simulator, and the API contract that the React frontend consumes. The work was recognized as the strongest architectural design across every group in the program.

The Optimization Engine

The core of the system is a cvxpy program that solves eight distinct portfolio construction objectives. Minimum variance and target return are straightforward quadratic programs. Maximum Sharpe is not, because a ratio of a linear numerator to a quadratic denominator is non convex in the weights. The engine handles this with the Charnes and Cooper transformation, which exploits the scale invariance of the Sharpe ratio to rewrite the problem as an equivalent convex program in a rescaled variable. Conditional Value at Risk is formulated through the Rockafellar and Uryasev linear program, which turns a tail risk measure that looks combinatorial into something a solver can handle directly. Risk parity uses a convex log barrier reformulation, and maximum diversification and net of cost objectives round out the set.

Constraints matter as much as objectives. The engine supports long only portfolios, per asset weight bounds, sector exposure limits, turnover caps, and no trade bands, all of which map cleanly onto the convex formulation without breaking solver guarantees.

Risk Estimation

A mean variance optimizer is only as trustworthy as the covariance matrix it is handed. Sample covariance is notoriously ill conditioned when the number of assets approaches the number of observations, which produces optimal weights that are wildly sensitive to noise. PortfoliU therefore offers four estimators. Sample covariance is the baseline. Ledoit-Wolf shrinkage pulls the sample estimate toward a structured target and stabilizes the inverse. Exponentially weighted moving average estimation lets recent volatility dominate. A PCA factor model strips the estimate down to its leading components. Expected returns can be estimated directly from history or through Black-Litterman, which blends an equilibrium prior with subjective views.

Backtesting

Any optimizer looks brilliant when it is allowed to peek at the future. The backtesting engine runs walk forward, refitting the covariance and return estimates only on data available at each rebalance date, so lookahead bias never enters the simulation. Rebalancing cadence is configurable, transaction costs and turnover constraints are charged against the portfolio, and results are benchmarked against a broad index fund, an equal weight allocation, and a classic 60/40 split. The engine reports CAGR, Sortino ratio, Calmar ratio, alpha, beta, information ratio, and maximum drawdown rather than a single headline number.

Architecture

The backend is a FastAPI service using async SQLAlchemy against Supabase Postgres, with Redis caching in front of the market data layer so that repeated optimizations over the same universe never pay twice for the same price history. Market data flows through a pluggable provider interface. Financial Modeling Prep supplies real end of day pricing, and a deterministic synthetic provider stands in when no API key is present, which keeps the test suite hermetic and lets contributors run the stack cold. Authentication runs through Supabase with server side JWT verification against JWKS. Long running parameter sweeps execute as background jobs and stream their results to the client over WebSocket, rendering as an interactive Sharpe heatmap as the sweep fills in.

The frontend is React and TypeScript built with Vite, using TanStack Query to manage server state and Recharts to draw the efficient frontier, the weight allocations, the drawdown curves, and the live heatmap. Continuous integration gates every merge on linting across both halves of the stack and on eighty percent backend test coverage.

Murmur, a Distributed Strongly Consistent Key/Value Store

A single-node storage engine replicated across a cluster by a hand-written Raft, so every write commits through a majority quorum.

Source Code

Overview

Murmur is a distributed key/value store that keeps a replicated log consistent across a cluster of nodes even when machines crash, restart, or fall behind. A single-node storage engine sits underneath, and a hand-written implementation of the Raft consensus algorithm sits on top, coordinating the replicas so that clients see one coherent, linearizable store rather than a set of diverging copies. The goal was to build consensus from first principles rather than reach for a library, and to make every guarantee something the test suite can prove.

Consensus and Replication

The heart of the system is a from-scratch Raft. Leaders are chosen through randomized election timeouts, and a PreVote round guards against a partitioned node disrupting a healthy cluster by forcing needless elections. Once a leader is established it replicates its log to followers, and when logs diverge after a leadership change the leader repairs them through conflict backtracking, walking the follower's log backward until it finds the last point of agreement. Every operation commits only after a majority quorum has durably accepted it, which is what gives the store its strong consistency.

Durability and Recovery

Consensus is only as trustworthy as what survives a power loss. Murmur fsyncs its current term, its vote, and its log to disk before acting on them, so a node that crashes mid-election or mid-append recovers to a state Raft still considers valid. To keep the log from growing without bound it performs log compaction, and it brings lagging or newly added followers up to date by shipping a snapshot of committed state rather than replaying history from the beginning.

Exactly-Once Client Semantics

Retries are unavoidable in a distributed system, so a client that resends a request after a leader change must not have its operation applied twice. Murmur tags each client with an ID and each request with a sequence number, and the servers deduplicate on that sequence number so a repeated request returns the original result instead of mutating state again. This holds across leader changes, giving the store exactly-once semantics from the client's point of view.

Architecture and Testing

Consensus is written as a pure, I/O-free state machine. It takes in events and returns actions, touching no network or disk directly, which makes the tricky parts of Raft unit-testable without spinning up a runtime. A gRPC transport built on tonic and prost carries messages between nodes, and the whole system is verified by dedicated election, replication, persistence, and chaos test suites that inject crashes and partitions to confirm the invariants hold.

Core Capabilities

Leader Election with PreVote

Randomized election timeouts elect a leader, and a PreVote round stops a partitioned node from forcing disruptive elections.

Log Replication and Repair

Followers are kept in sync by append, and divergent logs are healed through conflict-backtracking repair after leadership changes.

Snapshots and Compaction

Log compaction bounds disk growth, and snapshot transfer brings lagging or new followers up to date quickly.

Exactly-Once Semantics

Client IDs and server-side sequence-number dedup make retried requests idempotent across leader changes.

Sable, an LSM-Tree Storage Engine

A durable, crash-recoverable key/value database built from scratch in Rust, modeled on LevelDB and RocksDB.

Source Code

Overview

Sable is a key/value database engine written from scratch in Rust, structured as a log-structured merge tree in the lineage of LevelDB and RocksDB. An LSM-tree turns random writes into fast sequential ones by buffering them in memory and flushing sorted runs to disk, then merging those runs in the background. The project was an exercise in building that design end to end, from the write-ahead log up through compaction, with durability that holds under crashes as the non-negotiable requirement.

Write Path and Durability

Every write first lands in a checksummed write-ahead log and a sorted, versioned in-memory memtable, so an acknowledged write is on durable storage before the client hears success. Recovery replays the log on startup and truncates a torn tail, the partial record a crash can leave behind mid-write, so the engine always recovers to a consistent point. The result is a simple contract: every acknowledged write survives a crash or a power loss.

Read Path and On-Disk Format

Flushed data lives in on-disk SSTables built from prefix-compressed blocks with per-block CRCs to catch corruption, and each table carries a Bloom filter so the engine can skip tables that cannot contain a key. Reads traverse the memtable and the sorted tables through a lock-free merged path, and MVCC snapshot isolation lets readers see a consistent view while writes continue. Leveled compaction merges overlapping tables in the background to keep read amplification and space under control.

Measured against RocksDB 8.10 on a 200,000-key workload, Sable sustained roughly half of a mature, production-grade engine's read and write throughput while serving negative lookups, queries for keys that do not exist, about 2.75 times faster. That speedup comes directly from the Bloom filters, which skipped 78.5% of disk probes on misses. Correctness is backed by unit, integration, and crash-recovery test suites.
