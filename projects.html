Distributed Systems · Rust · 2026 · Raft Consensus

Murmur, a Distributed Key/Value Store

A key/value store that stays consistent across a cluster of machines, built on a Raft implementation I wrote by hand.

Source Code

try it, a live raft cluster

Raft is the algorithm that keeps the copies agreeing on one history of writes, even when machines fail. Rather than describe it, here is a five-server cluster you can break. Click any server to crash or restart it; crash the leader and watch the survivors elect a new one. Writes keep committing as long as three of the five are up.

what it is

Murmur is a key/value store that runs across several machines and keeps them agreeing on a single, ordered history of writes, even when some of those machines crash or fall behind. Underneath sits an ordinary single-node engine. On top sits a Raft implementation I wrote from scratch, no consensus library. To a client it behaves like one store, not five copies that might quietly diverge.

why I built it

I kept reading that consensus is hard and mostly taking people's word for it. Building Murmur was how I stopped doing that. The rule I set was that every guarantee had to be something a test could show, not something I asserted in a comment. If I claimed a write survived a crash, a test had to crash the process and prove the write was still there.

how consensus works here

One server is the leader and the rest are followers. The leader takes every write, appends it to its log, and ships it to the followers, and a write only counts as committed once a majority have it on disk. Leaders are found by election. A follower that stops hearing from the leader times out and runs for the job. A PreVote step keeps a briefly partitioned server from bumping the term and forcing a pointless election when nothing was actually wrong. When two logs disagree after a leadership change, the new leader walks the follower's log backward to the last entry they share and overwrites from there.

surviving crashes

A node writes its term, its vote, and its log to disk with fsync before it acts on any of them, so a crash mid-election or mid-append leaves it in a state Raft still considers legal when it comes back. Logs do not grow forever. Murmur compacts them and ships a snapshot to any follower that has fallen too far behind, instead of replaying history from the first entry.

not applying anything twice

Networks drop responses, so clients retry, and a naive store would apply the same operation twice. Every client gets an ID and stamps each request with a sequence number. The servers remember the last sequence number they have seen from each client and hand back the original result for a repeat instead of running it again. That holds even when the retry lands on a different leader.

how it is built and tested

The consensus logic is a pure state machine, events in and actions out, with no sockets or disk of its own. That was a deliberate choice, because it lets the hard parts of Raft be unit-tested without standing up a network. gRPC over tonic and prost carries the real messages between servers. Four suites cover elections, replication, persistence, and chaos, the last of which injects crashes and partitions and checks that the invariants still hold.

core capabilities

Leader Election with PreVote

Randomized timeouts elect a leader, and a PreVote round stops a partitioned server from forcing disruptive elections.

Log Replication and Repair

Followers stay in sync by append, and divergent logs are healed by walking back to the last shared entry.

Snapshots and Compaction

Compaction bounds disk growth, and snapshot transfer brings lagging or new followers up to date fast.

Exactly-Once Semantics

Client IDs and per-client sequence-number dedup make retried requests safe across leader changes.

Sable, an LSM-Tree Storage Engine

A crash-safe key/value database I wrote from scratch in Rust, in the same family as LevelDB and RocksDB.

Source Code

what it is

Sable is a storage engine, the layer a database uses to actually put bytes on disk and get them back. It is built as a log-structured merge tree, the design behind LevelDB and RocksDB, which takes the scattered writes an application throws at it and turns them into fast sequential ones by batching in memory and flushing sorted files to disk. I built the whole path myself, from the write-ahead log up through background compaction, and treated crash-safety as the one thing I would not compromise on.

how data moves through it

the write path, and why it survives a crash

Every write goes two places before Sable admits it succeeded. It lands in a write-ahead log on disk, checksummed so corruption gets caught, and in a sorted in-memory table. If the process dies, startup replays that log and trims the torn tail, the half-written record a crash leaves behind, so recovery always lands on a clean boundary. The contract is deliberately boring. If Sable said a write succeeded, it is still there after a crash or a power cut.

the read path and on-disk format

Once memory fills up, the table is flushed to an SSTable on disk, made of sorted blocks, prefix-compressed to save space, each with its own CRC. Every SSTable carries a Bloom filter, a small probabilistic index that can say "this key is definitely not here" and let a lookup skip the file entirely. Reads merge the in-memory table and the on-disk files through a lock-free path, and MVCC snapshots let a reader see a stable view while writes keep coming. Leveled compaction runs in the background, merging overlapping files to keep reads and disk usage in check.

I benchmarked Sable against RocksDB 8.10, a database with a decade of tuning behind it, on a 200,000-key workload, mostly to see how far off a from-scratch engine would land. It held about half of RocksDB's read and write throughput, which I will happily take against that bar. The one place it won outright was negative lookups, keys that do not exist, where it ran roughly 2.75 times faster because the Bloom filters skipped 78.5% of the disk probes that would otherwise happen. Correctness is pinned down by unit, integration, and crash-recovery tests.

Losing to RocksDB on throughput and beating it on negative lookups taught me more than a clean win would have. Most of the gap is compaction tuning and cache design, and the win came from getting one data structure right.

Portfolio Optimization · SEO Tech Developer Program · 2026 · Backend Lead

Halo, Optimal Portfolio Construction via Convex Optimization

A full-stack platform that turns Markowitz mean-variance theory into a working solver, a backtester, and a product.

View Live Platform Source Code

overview

Most retail investing tools hand you a pie chart and hope you do not ask where the numbers came from. Halo answers the underlying question directly. Given a set of assets, what weights should you actually hold, and can that answer be defended instead of asserted? Modern portfolio theory frames this as a convex optimization problem, so I built the platform around a real solver rather than a rule of thumb. You pick tickers, choose an objective and some constraints, and the backend returns the optimal weights along with the efficient frontier around them.

It started as a project inside the SEO Tech Developer Program and turned into the thing I have put the most hours into. I led the backend, which meant owning the optimizer, the risk models, the market-data layer, the backtester, and the API contract the React frontend consumes. The program judged our architecture the strongest of any team in the cohort.

the optimization engine

At the center is a cvxpy program that handles eight different objectives. Some are easy. Minimum variance and target return are plain quadratic programs. Maximum Sharpe is not, because maximizing a linear-over-quadratic ratio is non-convex in the weights, so I use the Charnes-Cooper transformation, which leans on the Sharpe ratio's scale invariance to rewrite it as an equivalent convex program. Conditional Value at Risk goes through the Rockafellar-Uryasev linear program, which turns a tail-risk measure that looks combinatorial into something a convex solver can chew through. Risk parity uses a convex log-barrier form, and maximum diversification and net-of-cost round out the set.

Constraints matter as much as objectives, so the engine takes long-only rules, per-asset weight bounds, sector caps, turnover limits, and no-trade bands, all of which fold into the convex formulation without breaking the solver's guarantees.

risk estimation

An optimizer trusts whatever covariance matrix you feed it, and sample covariance is a bad thing to trust when you have nearly as many assets as data points, since the weights it produces swing wildly on noise. So Halo ships four estimators. Plain sample covariance serves as a baseline, Ledoit-Wolf shrinkage pulls the estimate toward something stable, an EWMA version lets recent volatility dominate, and a PCA factor model keeps only the leading components. Expected returns come either straight from history or from Black-Litterman, which blends a market-implied prior with your own views.

backtesting

It is easy to build a backtest that cheats by looking at data it would not have had. Halo's runs walk forward. At each rebalance it refits covariance and returns only on data available up to that date, so no lookahead creeps in. Rebalance cadence is configurable, trading costs and turnover are charged to the portfolio, and every run is measured against an index fund, an equal-weight book, and a 60/40 split. It reports CAGR, Sortino, Calmar, alpha, beta, information ratio, and max drawdown, not a single headline number.

Over a five-year walk-forward backtest the optimized portfolio beat every benchmark on a risk-adjusted basis, about 0.48 Sharpe against roughly 0.20 for the index, equal-weight, and 60/40 books, with positive alpha and a smaller drawdown. That edge comes from careful covariance estimation and cost-aware rebalancing, measured honestly with no lookahead, not from anything exotic.

architecture

The backend is FastAPI on async SQLAlchemy over Supabase Postgres, with Redis in front of the market-data layer so repeated optimizations over the same universe do not re-fetch the same price history. Data comes through a pluggable provider interface, with Financial Modeling Prep for real end-of-day prices and a deterministic synthetic provider that stands in when there is no API key, which keeps the tests hermetic and lets anyone run the stack cold. Auth is Supabase with server-side JWT verification against JWKS. Long parameter sweeps run as background jobs and stream their results over WebSocket, filling in an interactive Sharpe heatmap as they go.

The frontend is React and TypeScript on Vite, using TanStack Query for server state and Recharts for the efficient frontier, the weight breakdowns, the drawdown curves, and the live heatmap. CI blocks any merge that fails linting on either half of the stack or drops backend coverage below eighty percent.
